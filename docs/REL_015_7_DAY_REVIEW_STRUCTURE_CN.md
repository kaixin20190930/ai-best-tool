# REL-015 7 天游标复盘结构

更新时间：2026-07-28

状态：活跃执行说明

REL-015 的目标不是“再做一次 review”，而是把 10 个产品内容验证和 10 个目标站人工提交验证之后的 7 天游标复盘，固定成一套可重复、可追踪、可决定是否扩大的决策结构。

## 一、复盘目标

7 天游标复盘只回答四个问题：

1. 哪些验证结果是真的有效？
2. 哪些页面或目标站只是在试跑，但还不能扩大？
3. 哪些阻断是结构性问题，必须先改规则？
4. 什么时候可以从小样本转向批量扩展？

## 二、输入数据

复盘只使用真实数据，不使用模板猜测：

- PI-013 / PI-014 的产品证据和内容验证结果
- DT-013 / DT-014 的目标站规则和快照结果
- RM-010 到 RM-015 的 live / issue / blocked / retention / feedback 数据
- 后台人工处理记录
- GSC 或站内真实表现信号

## 三、复盘维度

### 1. 内容验证

看点：

- 产品事实是否稳定
- 价格、功能、限制是否仍然可追溯
- 是否出现冲突或污染
- 真实信号是否足够支撑继续索引

输出：

- `publish`
- `revise`
- `hold`

### 2. 目标站验证

看点：

- 是否存在账号、支付、验证码、人工审核等结构性障碍
- 是否能稳定拿到 submission / registration / pricing 入口
- 是否需要人工处理原因
- 是否要暂时 blocked 或降级为观察

输出：

- `active`
- `needs_review`
- `blocked`
- `retired`

### 3. 渠道回收

看点：

- 哪些渠道真的带来访问、注册、提交或付款
- 哪些渠道只是耗时
- 哪些渠道需要补文案、补素材、补跟进

输出：

- 保留
- 降级
- 暂停

### 4. 扩大范围判断

看点：

- 是否满足继续扩量的质量门槛
- 是否有足够的真实反馈支撑自动化
- 是否需要继续人工复核

输出：

- `expand`
- `continue_observe`
- `stop_and_fix`

## 四、7 天游标复盘流程

### Day 0：确认样本

- 选出已验证的产品内容样本
- 选出已验证的目标站样本
- 标记 blocked、needs_review、live、issue 四类结果

### Day 1-2：整理事实

- 汇总最新快照
- 汇总人工处理原因
- 汇总漏掉的字段和素材

### Day 3-4：判断偏差

- 对比预期结果和真实结果
- 找出哪些规则太宽、太严或不稳定
- 找出哪些页面/目标站已经可以放行

### Day 5：生成修正动作

- 要补什么字段
- 要改什么文案
- 要改什么状态机
- 要改什么复查节奏

### Day 6：决定是否扩大

- 如果真实信号稳定，扩大样本
- 如果仍然波动，继续观察
- 如果出现结构性问题，先修规则再扩量

### Day 7：写结论

- 这轮验证是否成功
- 下一轮应该做什么
- 哪些模块继续保持人工确认

## 五、复盘输出格式

每次 7 天游标复盘都应该输出这四项：

1. 验证结论
2. 结构性问题
3. 修正动作
4. 扩大或暂停决定

## 六、验收标准

REL-015 只有在以下内容齐备时才算真正完成：

- 7 天游标复盘结构已固化
- blocked / needs_review / active / retired 的处理逻辑可解释
- 人工处理原因可回写并在后台可见
- 后续复盘不需要重新发明流程

## 七、与现有 RM/REL 的关系

- RM-010 到 RM-015 负责结果复查与周报导出
- REL-013 / REL-014 负责样本验证
- REL-015 负责把样本验证后的 7 天游标结论固定下来，作为下一轮扩量或收口依据
