本文档只负责一件事：把现有分发模块从“渠道任务记录器”收口成可供真实产品长期使用、无需额外管理工具承接的 **AI Product
Distribution Workspace**。

---

## 一、审计结论

现有模块已经具备项目、渠道、任务、状态、UTM、结果、归因、目标站情报和管理端复盘等基础能力，但用户主流程尚未把这些能力连
接起来。

截至 2026-08-02 的完成度口径：

| 维度                         | 估算完成度 | 结论             |
| ---------------------------- | ---------: | ---------------- |
| 底层数据和基础服务           |        70% | 可以支撑后续收口 |
| 用户可见操作能力             |        50% | 可用于内部试运行 |
| 不依赖额外管理工具的完整闭环 |    35%–40% | 尚未达到         |
| 面向付费客户的产品可用度     |        40% | 暂不扩大付费承诺 |

核心断点：

1. 用户任务绑定的是渠道类型，而不是 Product Hunt、AlternativeTo 等具体目标站。
2. 目标站规则、收费、账号、验证码和表单字段只在管理端存在，没有进入用户任务。
3. 产品证据引擎、素材、目标站专属文案和任务预检没有形成连续链路。
4. 今日队列可以排序任务，但不能真正回答“今天去哪个网站、为什么、怎么发”。
5. 结果记录和复盘存在，但提醒、自动复查和用户周报没有完整进入用户工作区。
6. 多项目切换与任务创建存在归属风险，必须先修复再进行真实多产品试用。

因此，历史 `DP-010` 至 `DP-017`、`RM-010` 至 `RM-015` 的“已完成”解释为：**对应代码组件或管理端能力已经完成**，不代表目标
站级用户闭环已经验收完成。

## 二、最终产品定位

产品名称：

**AI Product Distribution Workspace**

核心承诺：

> 系统负责研究具体目标网站、准备材料、安排每日任务、记录结果、自动复查和总结经验；用户只负责外站登录、验证码、付款确认和
> 最终提交。

用户不应再需要使用：

- Excel 或 Google Sheets 记录网站和状态。
- Notion 保存文案、规则和提交说明。
- Trello、Asana 或日历安排跟进。
- 单独的 UTM 生成器。
- 单独的外链检查表。
- 单独的周报文档。

不可替代的外部动作：

- 在目标网站注册和登录。
- 完成 CAPTCHA、邮箱验证或身份验证。
- 确认目标站付款。
- 最终点击提交、发布社区帖子或发送邮件。
- 处理目标站编辑人员的人工沟通。

不做以下承诺：

- 自动绕过验证码或登录墙。
- 自动向社区、Reddit、GitHub 批量发帖。
- 保证 dofollow、收录、排名或流量。
- 用重复文案批量制造低质量链接。

## 三、产品设计原则

### 1. 以“今天做什么”为首页

用户登录后首先看到跨产品的 1–3 个最高价值动作，而不是一组统计卡片或全部任务。

每个动作必须直接回答：

- 哪个产品。
- 去哪个具体网站。
- 为什么现在做。
- 预计耗时和费用。
- 是否需要账号、验证码或人工审核。
- 使用哪个落地页和追踪链接。
- 复制哪些文案、上传哪些素材。
- 提交后点击哪个按钮。
- 下一次复查时间。

### 2. 一项任务对应一个产品和一个具体目标站

`channel` 只负责分类和统计，`target` 才是用户真正执行的对象。

不得再创建只有“AI Directory”“Reddit”“GitHub”而没有具体目标网站或具体社区位置的提交任务。研究类任务可以暂时没有目标站，但
进入 `ready_to_submit` 前必须绑定目标站。

### 3. 产品事实只维护一次

产品名称、定位、目标用户、功能、价格、竞品、Logo、截图、证明点和披露身份统一进入产品档案。所有目标站文案从该档案生成，用
户不需要在每项任务中重复输入。

### 4. 所有输出可追溯、可编辑、可复制

AI 生成的事实必须能回到产品证据；目标站规则必须显示来源 URL 和最后核查日期。文案必须允许人工编辑，并提供字段级复制，不把
用户锁在不可修改的生成结果中。

### 5. Fail closed

规则不明确、事实冲突、素材缺失或目标站信息过期时，系统必须标记需要复核，不能自动假设免费、dofollow 或可以提交。

### 6. 每次人工动作都产生结构化学习

用户只需选择结果和补充最少必要信息。拒绝、收费变化、验证码、账号限制、表单变化和 live URL 都应反向更新目标站档案和后续排
序。

## 四、完整用户旅程

### 阶段 A：创建并校准产品

1. 用户输入产品官网 URL。
2. 系统读取已有 Product Intelligence Profile；没有则启动受控发现和证据提取。
3. 系统展示产品名称、定位、目标用户、核心功能、价格、竞品、Logo、截图和证明点。
4. 用户只确认或纠正无法从公开官网验证的内容。
5. 用户选择本轮目标：品牌曝光、目录收录、推荐流量、launch、社区反馈、newsletter 或高质量 backlink。
6. 用户设置每周可投入时间、可接受费用和优先市场。
7. 系统给出“准备度”和缺失素材清单。

完成条件：产品事实已确认、至少一个有效落地页、基础 Logo 和截图齐全，或明确标记缺失。

### 阶段 B：生成目标站机会池

1. 系统从目标站 registry 中筛选与产品匹配的网站。
2. 每个目标站显示适配分、推荐理由、成本、预计耗时、账号要求、验证码、审核周期和历史保留率。
3. 系统过滤已提交、已拒绝且尚不可重试、规则过期、低相关性或高风险目标。
4. 用户可以接受推荐、稍后处理或永久跳过，并填写原因。
5. 系统为接受的目标站创建 `project_target` 机会记录，而不是立即制造大量任务。

完成条件：每个候选都有明确目标站、规则快照、适配理由和下一步。

### 阶段 C：准备目标站专属材料包

系统按 `project + target` 生成：

- 推荐落地页和 UTM 链接。
- 多长度标题、一句话介绍、短描述和长描述。
- 主要功能、目标用户、分类和标签建议。
- Alternative 定位、Founder story、Newsletter pitch、社区和 Reddit 披露版本。
- 邮件主题和正文。
- 目标站字段映射。
- Logo、截图、视频和尺寸清单。
- 提交前检查项。
- 可能拒绝原因和建议跟进日期。

用户可以逐字段编辑、复制，并下载该目标站需要的素材。

完成条件：事实门槛通过、长度符合要求、必填字段和素材齐全、追踪链接可用。

### 阶段 D：执行今日任务

工作台每天默认展示 1–3 项：

1. 打开任务详情。
2. 查看为什么推荐、预计耗时和风险。
3. 点击“打开提交页”。
4. 在本平台逐字段复制文案、下载素材。
5. 在目标站完成登录、验证码和最终提交。
6. 回到本平台点击“已提交”“遇到阻碍”或“放弃”。
7. 系统自动记录时间并生成后续复查。

理想操作要求：准备完成后，从打开任务到记录提交结果不超过两个平台内操作步骤；用户不需要重新搜索提交地址或打开第三个管理工
具。

### 阶段 E：审核、上线和复查

- `submitted + 3 天`：检查是否需要补充资料。
- `submitted + 7 天`：提醒人工查询审核结果。
- `live + 7 天`：检查页面和链接。
- `live + 30 天`：检查保留、访问和转化。
- `live + 90 天`：检查长期保留并更新渠道评分。

系统自动检查可访问性、重定向、页面标题、产品名称、链接存在性、rel 属性和 UTM 归因。无法自动确认时进入人工复核收件箱。

### 阶段 F：周报和下一周计划

用户工作区直接显示：

- 本周完成、提交、审核中、上线、拒绝和阻塞数量。
- 每个产品的推进情况。
- 新增 live URL 和链接属性。
- 渠道带来的访问、注册和付款。
- 主要拒绝与阻碍原因。
- 应停止、继续或扩大投入的渠道。
- 下一周建议的 3–10 项任务。

## 五、信息架构与页面方案

### 1. `/[locale]/distribution`

升级为跨产品 Distribution Home：

- 今日 1–3 项。
- 阻塞和待人工确认收件箱。
- 本周进度。
- 产品切换和全部产品视图。
- 最近上线、拒绝和链接异常。
- 下一周建议。

### 2. `/[locale]/distribution/projects/new`

产品初始化向导：

- 官网导入。
- 产品事实确认。
- 目标和预算。
- 素材准备度。
- 推荐目标站预览。

### 3. `/[locale]/distribution/projects/[projectId]`

单产品控制台：

- 产品档案与准备度。
- 推荐目标站。
- 今日任务。
- 全部机会和任务。
- 素材库。
- 结果与归因。
- 周报。

### 4. `/[locale]/distribution/projects/[projectId]/targets`

目标站机会池：

- 推荐、实验、需判断、不推荐。
- 免费/付费、账号、验证码、审核时间筛选。
- 已提交和未提交去重。
- 接受、稍后、跳过。

### 5. `/[locale]/distribution/tasks/[taskId]`

升级为 Execution Cockpit：

- 具体目标站信息和适配理由。
- 提交、注册、价格和规则来源链接。
- 字段级材料包和一键复制。
- 素材下载与缺失提示。
- 追踪链接。
- 提交检查清单。
- 打开目标站。
- 已提交、阻碍、拒绝、上线等快速操作。
- 下次跟进和历史状态时间线。

### 6. `/[locale]/distribution/assets`

产品素材中心：

- Logo、icon、截图、视频、头像和品牌文字。
- 文件用途、尺寸、来源、最后更新和验证状态。
- 按目标站显示缺失项。
- 目标站任务内直接选择和下载。

### 7. `/[locale]/distribution/reports`

用户自己的项目周报和渠道效果，不再只存在于管理后台。

### 8. `/[locale]/admin/targets`

继续作为平台级目标站 registry，负责规则修正、失效站点、收费变化、抓取失败和人工验证，不暴露其他用户私有数据。

## 六、数据模型收口

采用向后兼容的增量迁移，不直接破坏现有任务和结果。

### 1. `distribution_projects` 增强

新增建议字段：

- `intelligence_profile_id`
- `primary_goal`
- `weekly_capacity`
- `budget_preference`
- `target_markets`
- `onboarding_status`
- `facts_confirmed_at`

保存：

- `project_id`
- `asset_type`
- `name`
- `url` 或 storage path
- `width` / `height`
- `source_url`
- `verified_at`
- `status`
- `metadata`

### 3. 新增 `distribution_project_targets`

连接产品与具体目标站：

目标站 registry 和规则快照保存在 Neon，用户项目与任务保存在 Supabase；`target_id` 是稳定的跨库 UUID 引用，不建立数据库外键。服务端负责验证目标站存在，并把 Neon 的 `channel_key` 映射到 Supabase 的渠道 ID。

- `project_id`
- `target_id`
- `match_score`
- `match_reasons`
- `opportunity_status`
- `estimated_minutes`
- `estimated_cost`
- `selected_at`
- `skipped_reason`
- `last_submission_at`
- `next_action_at`

唯一约束：`project_id + target_id`。

### 4. `distribution_tasks` 增强

新增：

- `target_id`，研究任务可空，提交任务必须有值。
- `project_target_id`
- `distribution_link_id`
- `estimated_minutes`
- `blocked_reason`
- `submitted_at`
- `next_action_at`
- `completed_at`
- `assigned_to`，P2 团队协作使用。

首先修复所有 create action 必须显式接收并校验当前 `project_id`，不得静默回退到默认项目。

### 5. 新增 `distribution_packages`

保存目标站级材料包：

- `project_id`
- `target_id`
- `task_id`
- `profile_version`
- `target_rule_version`
- `fields_json`
- `asset_requirements_json`
- `preflight_json`
- `generation_status`
- `approved_at`

材料包必须锁定产品事实版本和目标站规则版本，便于解释历史提交内容。

### 6. 新增 `distribution_task_events`

保存状态时间线和人工反馈：

- 状态变化。
- 阻碍类型。
- 用户备注。
- 规则变化。
- 提交、审核、上线和移除时间。

### 7. 新增 `distribution_reminders`

保存：

- `task_id`
- `reminder_type`
- `scheduled_at`
- `status`
- `delivery_channel`
- `sent_at`
- `resolved_at`

### 8. 权限和隐私

- 用户只能读取自己的 workspace、project、asset、task、result、package、event 和 reminder。
- 目标站公开规则由平台维护，用户可读但不可直接覆盖共享事实。
- 用户提交的账号信息不保存密码；只保存 `account_ready` 等状态。
- 管理后台汇总不得展示其他客户的私有文案、素材和备注。

## 七、调度与推荐规则

每个候选任务计算 0–100 的执行优先分：

| 维度                 | 权重 |
| -------------------- | ---: |
| 产品与目标站适配分   |   25 |
| 材料和素材准备度     |   20 |
| 截止日期和跟进时机   |   15 |
| 历史通过率与保留率   |   15 |
| 预计时间和成本       |   10 |
| 当前产品增长目标     |   10 |
| 重复、拒绝和垃圾风险 |    5 |

硬性过滤：

- 已提交且未到复查时间。
- 已 retired 或明确不相关。
- 规则过期且风险高。
- 产品事实存在严重冲突。
- 必填素材缺失且无法在当天补齐。
- 同一产品和目标站已有开放任务。

每日队列默认最多 3 项；Agency 可以查看团队容量，但仍不鼓励批量低质量提交。

## 八、通知、自动检查与异常降级

### 平台内通知

- 今日任务到期。
- 审核等待超期。
- 缺失素材。
- 目标站规则变化。
- live URL 失效或链接被移除。
- 周报已生成。

### 邮件摘要

- 默认每日一封摘要或每周一封周报，用户可关闭。
- 不为每个小状态发送单独邮件。

### 自动检查失败

- 登录墙或 CAPTCHA：转人工确认，不重复抓取。
- 目标站超时：保留旧规则并标记过期，不覆盖为错误结论。
- 外站阻止机器人：创建人工复查任务。
- 归因不可用：结果仍可保存，不阻塞提交流程。
- AI 生成失败：保留已有人工内容并允许重新生成单个字段。

## 十、实施顺序与发布策略

### 批次 1：修正数据正确性

执行 `DC-010`、`DC-011`。

- 先增加可空字段和新表。
- 不删除旧状态和旧任务。
- 回填可确定的 project/channel 关系。
- 旧任务显示为“待绑定具体目标站”。
- 本地 migration verify、类型检查和完整 build 通过后才进入生产迁移。

### 批次 2：连接产品、目标站和材料

执行 `DC-012` 至 `DC-016`。

- 复用 Product Intelligence，不重复建设抓取系统。
- 复用已有 target registry，不另建目标站列表。
- 文案绑定 profile version 和 target rule version。
- 没有可靠事实时阻断生成，而不是生成泛化营销句。

### 批次 3：执行页和自动复查

执行 `DC-017`、`DC-018`。

- 优先优化单任务执行体验。
- 再连接 follow-up、live check 和 reminder。
- 所有自动化保持可观察、可重试和可人工覆盖。

### 批次 4：真实产品验收

执行 `DC-019`。

- 先选 3 个用户自己的产品。
- 每个产品选择 3 个差异明显的目标站。
- 至少覆盖免费目录、需要账号、人工审核、收费或验证码中的三类情况。
- 每个断点必须记录为任务或缺陷，不在外部表格维护。

### 批次 5：无外部工具验证

执行 P1，并连续运行 7 天。

只有用户能够连续 7 天只使用本平台和目标站完成工作，才可以宣称“不需要额外的分发管理工具”。

## 十一、测试与验收

### 自动测试

- 多项目任务归属和越权测试。
- RLS：不同用户不能访问彼此项目、素材、材料包和结果。
- 旧任务兼容和迁移幂等测试。
- 目标站规则版本绑定测试。
- 产品事实冲突阻断测试。
- 字符限制、必填字段和素材预检测试。
- UTM 唯一性和归因测试。
- 状态机及重复提交防护测试。
- 3/7/30/90 天提醒计算测试。
- live URL 检查失败降级测试。

### 页面验收

- 桌面和移动端均可完成核心流程。
- 所有复制按钮有明确成功反馈。
- 所有外站链接新窗口打开并保留当前任务状态。
- 表单错误直接显示，不依赖服务端日志。
- 长文案、长 URL 和大量任务不破坏布局。
- 空状态明确告诉用户下一步，而不是只有空白统计。

### 生产验收

- `pnpm run build` 通过。
- migration verify 通过。
- Distribution production smoke 通过。
- 登录、权限、Stripe entitlement 不回归。
- 三个真实产品各完成三个目标站。
- 访问、提交、live URL 和 follow-up 数据正确。

## 十二、职责分工

### Codex 负责

- 数据模型、迁移、RLS 和兼容回填。
- 产品初始化、目标站推荐、材料包和执行页。
- 调度、提醒、复查、周报和通知。
- 自动测试、build、smoke 和文档状态。
- 根据真实测试结果修复流程断点。

### 用户负责

- 提供并选择首批 3 个真实产品。
- 确认无法从官网验证的第一方事实。
- 在目标站完成账号、验证码、付款和最终提交。
- 将目标站实际反馈通过平台结构化记录。
- 确认邮件发送配置和商业套餐边界。
- P2 阶段选择外部试用用户。

## 十三、Definition of Done

分发模块只有同时满足以下条件才算完整收口：

1. 任务明确绑定产品和具体目标站。
2. 用户能看到提交入口、收费、账号、验证码、审核周期和规则来源。
3. 产品事实和素材只维护一次，可供所有任务复用。
4. 每个目标站得到独立、可追溯、可编辑、可复制的材料包。
5. 用户不需要表格、Notion、日历或单独 UTM 工具。
6. 提交、审核、上线、阻塞、拒绝和移除都有完整时间线。
7. 3/7/30/90 天复查自动生成并可通知。
8. 用户自己的周报能说明进展、结果、阻碍和下周动作。
9. 多项目归属、权限、迁移、build 和 production smoke 全部通过。
10. 三个真实产品完成端到端试用，并连续 7 天无外部管理工具遗漏。

在此之前，产品对外描述应使用“分发试运行工作台”，不能声称已经完全自动研究、准备和跟进所有分发工作。
